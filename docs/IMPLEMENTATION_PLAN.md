# ねこ茶屋 実装計画

- バージョン: 0.1
- 前提: `GDD.md` v0.2 / `TECH_DESIGN.md` v0.2
- 方針: 依存の少ない下層(game-core)から積み上げ、**各フェーズの終わりに必ず動くもの・
  検証できるものがある** 状態を保つ。描画(Pixi)は最後から2番目 — それまでは仮UIで遊べる

## フェーズ一覧

| フェーズ | 内容 | 完了時にできること |
|---------|------|------------------|
| 0 | プロジェクトセットアップ | dev サーバーとテストが走る |

## フェーズ 1: game-core — シミュレーション(純ロジック)

React・Pixi・localStorage に一切触れない。TDD で進める価値が最も高い層。

**成果物**
- `types.ts`(GameState / derived / Decimal 型の別名)
- `data/generators.ts` `data/upgrades.ts`(GDD §4・§6 のマスタ)
- `formulas.ts`: コスト(1.15^owned)、マイルストーン(10/25/50/100)、
  globalMult(1 + 0.10×猫玉)、tapGain、猫玉獲得式
- `derived.ts`(recomputeDerived)/ `initial.ts`(createInitialState)
- `advance.ts`(構造共有を守る)/ `actions.ts`(buyGenerator / buyUpgrade / tap / prestige)

**テスト(TECH §13 のうち formulas 分)**
- コスト成長・マイルストーン境界(9→10体、24→25体 …)
- 猫玉: 獲得0クランプ、所持数との差分、転生後の lifetimeKoban 保持
- tap: 生産0時の下限×globalMult、tapMult 乗算
- advance: dt 比例、derived 未変更時の参照維持(構造共有)

**完了条件**: 上記テスト全グリーン。カバレッジは game-core の主要分岐を網羅

## フェーズ 3: ストア・ゲームループ・永続化の配線

初めてブラウザで動かすフェーズ。UI はデバッグ用の素の数値表示+ボタンで良い。

**成果物**
- `store/gameStore.ts`: zustand。全アクション `set(prev => …)` 関数型アップデータ、
  Decimal カスタム equality、subscribeWithSelector 導入
- `loop/useGameLoop.ts`: rAF + 固定タイムステップ(TICK 0.1s、acc クランプ 1s)
- `store/persistence.ts`: 起動フロー(セーブなし→initial / あり→migrate→deserialize→
  recomputeDerived→offline)、autosave 10s、visibilitychange 保存+復帰分岐(60秒閾値)
- `store/tabLock.ts`: ハートビートロック(2s/5s)、非リーダーの停止フラグ、
  新しい savedAt を上書きしない保存ガード
- デバッグページ: 所持小判・生産/秒の表示、tap / buy ×8 / prestige の素ボタン

**完了条件(手動確認)**

- タブを閉じて再度開くとオフライン収益が計算される(60秒未満/以上の分岐)

## フェーズ完了レビュー(必須ゲート)

各フェーズの完了条件を満たしたら、コミットの前に **複数の新規サブエージェント**(そのフェーズの
実装に関与していない、まっさらなコンテキストのエージェント)に並列でレビューさせる。
レビュー観点はフェーズ内容に合わせて 2〜3 本を選ぶ:

| 観点 | 内容 | 主な対象フェーズ |
|------|------|----------------|
| 仕様準拠 | GDD/TECH_DESIGN と実装の突き合わせ。数式・閾値・挙動の一致 | 1, 2, 3, 4 |
| コード品質・バグ | ロジック誤り、エッジケース漏れ、レイヤー違反、テストの穴 | 全フェーズ |
| UX・挙動 | 実際の操作フローの破綻、表示崩れ、フィードバック不足 | 4, 5, 6 |

- 指摘は「採用/棄却+理由」を判断してから反映する(全部鵜呑みにしない)
- 仕様側の誤りが見つかった場合は GDD/TECH_DESIGN を先に修正する(ドキュメントが常に正)
- レビュー反映後にテストを通し、それからコミット・プッシュする

## Codex MCP の活用

実装中は Codex MCP(`mcp__codex`)をセカンドオピニオン・相互チェックとして適切な
タイミングで併用する。使いどころの目安:

- **難所の実装前の壁打ち**: Pixi v8 の async init と React StrictMode の共存(フェーズ5)、
  マルチタブロック(フェーズ3)など、設計書に手順はあるが実装が繊細な箇所
- **ロジックの相互検証**: game-core の数式・オフライン計算・マイグレーション(フェーズ1〜2)を
  実装後に Codex に読ませ、仕様との齟齬や境界バグを別視点で探させる
- **行き詰まったバグ**: 自力のデバッグが2〜3手で決着しないとき、早めに Codex に状況を渡して
  仮説を出させる
- フェーズ完了レビューのサブエージェントレビューとは別枠(Codex は実装中の随時利用、
  サブエージェントレビューはフェーズ末の必須ゲート)

## 完全自走運用と議事録(フェーズ0〜6)

フェーズ0〜6は Claude が **完全自走** で実施する(フェーズごとのユーザー承認を待たない)。
その際、以下を義務とする。

- **問題発生時はサブエージェントと相談して方針決定する。** 「問題」とは:
  仕様・設計ドキュメントの穴や矛盾の発見、技術的ブロッカー(設計書どおりに実装できない)、
  フェーズ完了条件を満たせない事態、レビュー指摘同士の対立、など。
  独断で設計を変えず、複数サブエージェント(必要に応じて Codex MCP も)に意見を出させ、
  比較したうえで方針を決定する
- **相談・決定のたびに議事録を作成する。** `docs/minutes/NNN-<topic>.md`(NNN は連番)に、
  以下の形式で残す:
  - 議題 / 背景(何が起きたか)
  - 相談相手と各意見の要旨(サブエージェント・Codex の見解)
  - 決定事項と理由(採用しなかった案にも一言)
  - 影響(GDD / TECH_DESIGN / 本計画の修正箇所、コードへの反映)
- 議事録と、それに伴うドキュメント修正は当該フェーズのコミットに含めてプッシュする
- 軽微な実装判断(変数名、ファイル分割など仕様に影響しないもの)は議事録不要。
  仕様・設計・計画のいずれかに影響する判断はすべて議事録の対象

## フェーズ横断の運用ルール

- 仕様の解釈に迷ったら実装で勝手に決めず、GDD/TECH_DESIGN を修正してからコードに反映
  (ドキュメントが常に正)
- 各フェーズ完了時に `npm test` / `npm run typecheck` / `npm run build` を通し、
  フェーズ完了レビューを経てからコミット
- game-core に React/Pixi/DOM への import が入ったらレビューで弾く(レイヤー違反)
